## 3. 统榜数据口径

### 个人成绩

- 有效对局必须同时满足：`started_at >= 比赛开始时间`、`ended_at <= 比赛结束时间`。
- 个人基础成绩暂定为比赛期间分数最高的 3 把；不足 3 把时保留缺口，不用比赛外成绩补齐。
- 每把同时保留单局分数和盘面和，不能用其中一个字段覆盖另一个字段。

### 队伍成绩

- 队伍由导入名单决定；不在本阶段实现自动分组或实力均衡算法。
- 队伍总分暂定按队员有效成绩的盘面和汇总，展示名称使用“总盘面和”。
- 队伍表头使用：`排名`、`队伍`、`总盘面和`、`完成率`；其中 `总盘面和` 和 `完成率` 使用较大字号突出显示。完成率按 `已打局数 ÷ (12 人 × 3 局) × 100%` 计算。
- 每名队员使用单行成绩结构：`队员号`、`Verse`、`档排`、`Top1`、`Top2`、`Top3`、`总盘面和`；不显示选手名或 rating。`档排`同分并列，无成绩显示 `—`。
- 每名成员先按单局分数取最高三局，再用这三局的盘面和求 `总盘面和`；队伍总盘面和为名单内成员总盘面和之和。

### 个人榜

- `赛时单局榜Top20`：汇总所有队伍和个人组玩家，按比赛期间单局分数排序；只展示 `名次`、`组别`、`Verse`、`单局分数`。
- `赛时盘面和榜Top15`：汇总所有队伍和个人组玩家，按个人赛时总盘面和排序；只展示 `名次`、`组别`、`Verse`、`赛时总盘面和`。
- 个人组表头使用“个人组”，不计算或展示平均 rating。


## 4. 两张榜图格式与数据契约

### 4.1 固定版式

- `总榜.png`：左侧为 6 行队伍总榜；中间为 20 行 `赛时单局榜 Top20`；右侧为 15 行 `赛时盘面和榜 Top15`。总榜保留顶部 `群星杯 · 2026 4×4 团体赛` 表头。
- `六队明细.png`：六张队伍卡片按 A–F 固定顺序 3×2 排列，每张固定 12 个成员行；顶部五个状态框字号已放大。队名、`第N名`、队总盘面和、完成率为卡片头部信息，其中后两项使用较大字号并横向放在名次右侧。卡片表头为 `队员号`、`Verse`、`档排`、`Top1`、`Top2`、`Top3`、`总盘面和`；不显示个人组。
- 两张图均由独立背景和内存中的数据层合成。背景只负责美术，数据层只负责文字和线框；正式输出不再额外生成内容透明 PNG。

### 4.2 榜图快照 JSON

每次发布先固定一份 `榜图数据.json`，渲染器不直接从 Bot、NapCat 或 QQ 读取数据。最小结构如下：

```json
{
  "required_games": 3,
  "event": {
    "title": "群星杯 · 2026 4×4 团体赛",
    "subtitle": "2026.07.27 — 08.24 · 2048 4×4 团体赛",
    "start_time": "2026-07-27 00:00:00",
    "end_time": "2026-08-24 23:59:59",
    "as_of": "2026-07-27 12:00:00",
    "event_code": "STAR_2026_4X4"
  },
  "teams": [
    {
      "code": "A",
      "name": "星河",
      "rank": 1,
      "total_board_sum": 1520909,
      "completion": {"completed": 11, "total": 12},
      "players": [
        {
          "number": "01",
          "username": "verse_account_key",
          "verse": "v_01",
          "top_scores": [438040, 212698, 0],
          "total_board_sum": 103414
        }
      ]
    }
  ],
  "individuals": [],
  "single_game_top": [{"verse": "v_25", "group": "C", "score": 837317}],
  "board_sum_top": [{"verse": "v_13", "group": "B", "board_sum": 130401}]
}
```

实际文件中的 `teams` 必须符合本次比赛名单和榜图布局；每名成员最多保留 3 把成绩。`single_game_top` 和 `board_sum_top` 可以不提供，渲染器会从成员数据生成；正式发布建议在快照中明确写入，保证人工复核时输入完整。`display_name`、`rating`、`team_rating` 和 `rating_top` 不属于榜图输出契约。

本次比赛专用名单模板为 `config/annual_4x4_2026_roster.template.json`。名单在比赛前一晚填入；榜图程序只对名单内玩家生成成绩，不根据数据库中的其他玩家自动扩展名单。

本次实际名单已经导入 `config/annual_4x4_2026_roster.json`。群星杯专用入口的常用命令为：

```bash
python event_hub.py
# 菜单：1 导入名单、2 补录、3 增量查询、4 生成榜图、5 全量查询、0 退出

python event_hub.py import-roster /home/oracle_f/下载/群星杯分队.xlsx --force
python event_hub.py query
python event_hub.py export
```

默认缓存位于 `data/tmp/annual_4x4_2026_live_cache.json`，其中保存每次成功查询的模式、起止时间、开始/完成时刻、玩家数、当次读取记录数和缓存总记录数。通常先执行查询，再按需要反复生成图片；生成过程不会访问 Verse。如需赛前或赛后做一次从比赛起点开始的完整复核，可运行 `python event_hub.py query --full`。并发数可用 `query --workers` 在 1–32 之间调整，默认 8；不建议无依据调高。多轮重试后仍失败时，详情会写入 `data/tmp/annual_4x4_2026_last_query_failure.json`。

再次使用 `import-roster --force` 更新正式名单时，会按 Verse 名保留已有人工补录，避免 XLB 成绩被名单覆盖；名单和榜图快照均使用临时文件后原子替换。

XLB 的人工补录记录直接写入专用名单，并参与同一套“按分数取前三局、按盘面和汇总”的计算：

```bash
python event_hub.py supplement \
  --player XLB \
  --score 500000 \
  --board-sum 3000 \
  --note "人工核验"
```

补录记录的开始/结束时间可以不填；如果填了，程序仍会按群星杯固定时间窗校验。普通玩家不能走这个人工补录入口，避免同一局被数据库和人工记录重复计算。

### 4.3 每次实际比赛生成流程

1. 先按比赛时间窗结算数据：只接受 `started_at >= start_time` 且 `ended_at <= end_time` 的完整对局；每位成员按单局分数取最高的 3 把，再将这 3 把的盘面和相加得到个人赛时总盘面和。
2. 固定队伍名单和当前数据截至时间，生成一份新的 `榜图数据.json`；不要覆盖上一时刻的输出目录。
3. 用快照生成两张合成图和一份榜图数据快照：

   ```bash
   cd /home/oracle_f/文档/Codex/2026-04-25/2048Event/赛事中台
   python scripts/export_match_rank_images.py \
     --snapshot /path/to/榜图数据.json \
     --background ../比赛导出/设计草图/统榜_共享背景_群星杯与尚竞之勇_v8_1920x1080.png \
     --output-dir ../比赛导出/正式榜图/STAR_2026_4X4/20260727_120000
   ```

4. 人工检查 `总榜.png`、`六队明细.png` 和 `榜图数据.json`，确认比赛日期、榜单排序、缺成绩显示和线框完整后再发布。
5. 发布先采用手动发图；Bot 或其他发送渠道只作为后续入口，发送失败不影响快照和图片生成。

本次比赛不需要从数据库查找赛事 event code。比赛前一晚填好专用名单文件后，直接使用固定时间窗运行：

```bash
python scripts/export_annual_4x4_rank_images.py \
  --db data/tournament_hub.sqlite3 \
  --roster config/annual_4x4_2026_roster.json \
  --output-dir ../比赛导出/正式榜图/年度4x4_2026/20260727_120000
```

该专用模式不会写入数据库；它只读取固定比赛时间窗内、名单中账号的有效记录，先生成快照，再输出榜图。

## 6. 实施顺序与优先级

### P0：数据契约和正确性

1. 增加比赛专用名单配置：比赛开始/结束时间、模式、Top3 规则和榜图数据截至时间。
2. 增加队伍及成员导入结构；导入时检查重复玩家、缺失玩家和未知 Verse 用户。
3. 实现严格时间窗过滤、个人 Top3、队伍总盘面和、完成率及排名计算。
4. 为时间边界、不足三把、重复导入、缺失开始/结束时间和个人组加入回归测试。

不做的后果：没有稳定的数据契约就开始画图，后续改计分口径会同时返工数据库、榜图和 Bot 发送流程。实现复杂度中等偏高，优先级最高。

### P1：每日榜快照与榜图

1. 将某一时刻的计算结果保存为每日快照，避免重复抓取导致同日榜图不一致。
2. 按当前两图结构生成 PNG；先支持手动运行和人工审核。
3. 确认字体、长名字、缺成绩、超出 72 人和个人组数据进入 Top 榜时的版面降级规则。

不做的后果：只能临时手工拼表，无法复现当天榜单。实现复杂度中等，优先级高。

### P2：发布与自动化

1. 先支持“手动运行统榜程序，再手动发群”。
2. 稳定后再增加定时统计，最后再考虑 Bot 自动发送。
3. Bot 发送失败时只记录并提示，不阻塞榜单生成，也不在群内刷屏。

不做的后果：每天需要人工发图，但不影响统计正确性。实现复杂度低到中等，优先级低于 P0/P1。

## 7. 未决事项

- 比赛结束时间和每天数据截至时间。
- 报名超过 72 人时是扩大每队人数、增加个人组，还是同时采用两者；当前只保留可扩展的数据结构。
- 个人组人数上限及个人组在单图中的最终占位方式。

## 8. 验收标准

- 同一份导入名单重复运行不会重复计入队伍或成员。
- 比赛开始前或结束后的对局不会进入任何个人 Top3、队伍总盘面和或完成率。
- 每名成员最多显示三把，三把分别有独立的分数和盘面和列。
- 队伍榜、单局榜、盘面和榜对个人组玩家的归属一致。
- 榜图及其 `榜图数据.json` 只包含 Verse 和盘面和相关字段，不包含选手名或 rating。
- 榜图中 6 队全部出现，缺少成绩时不挤乱其他成员行；每名成员的三把成绩分别落在 Top1/Top2/Top3 列。
- 生成失败、数据不完整或 Bot 发送失败时，不影响上一份有效快照，也不造成群刷屏。
- 人工补录玩家不参与 Verse 账号查询；补录的分数与盘面和能正确进入个人 Top3、队伍总盘面和及完成率。
- 六队明细固定按 A–F 排列；队伍名次按队总盘面和重算，同分并列、全队尚无成绩时卡片写“未排名”且总榜名次显示 `—`；每档六人按个人赛时总盘面和生成 `tier_rank`，榜图显示为普通黑色数字。
